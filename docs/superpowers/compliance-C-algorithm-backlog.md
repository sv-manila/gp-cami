# Compliance Audit C — Algorithm, Scale & Backlog

Auditor lane: Recommendations & Open Risks (4153573388), Cross-Source Matching Appendix (4148592642),
Incremental Profiling (4153442305), Scaling & Performance (4153278465), Success Metrics & Risks
(4067295233). Audited against the ten plans in `docs/superpowers/plans/`, `00-PROGRAMME.md` as

## 0. Framing: which engine each source page is about

"Recommendations & Open Risks" audits `sv-manila/profiling` — a **Python** engine (ChromaDB,
SentenceTransformer, `MATCH_THRESHOLD`, `compute_similarity`). gp-cami is PHP/Laravel/MySQL, a
different codebase. Of that page's 8 backlog rows, **3 are about the Python engine only** and do
not translate to gp-cami at all (see §1, rows 2, 4, 7). The Cross-Source Matching appendix and
Scaling & Performance page assume a multi-warehouse-table, Spark/Glue/GraphFrames architecture,
which decision §8 of `PROJECT_PLAN.md` (cited in the task as already-made) rejects for gp-cami — so
large parts of those two pages are OUT OF SCOPE by architecture, not by neglect. I separated the
architecture-bound material from the portable underlying requirement (e.g. "cap oversized blocks"
survives even though "run it on Spark" does not).

## 3. Incremental Profiling (4153442305) — plan 8's page

| # | Requirement | Verdict | Evidence |
|---|---|---|---|
| 1 | Three persistent structures: crosswalk, inverted `block_key → {profile_id}` index, profile signature | **COVERED** | Crosswalk: pre-existing `gp_source_link`, untouched (plan 8 self-review item 1). Inverted index: **built**, `gp_identity_block_key` (Tasks 1-3, incremental-profiling.md:198-874), maintained by both the per-row (`DeterministicResolver`) and bulk (`SetFinalizer`) paths, consumed by `ProbabilisticResolver`'s candidate lookup and `block_size_cap` check. Profile signature: **built**, `gp_identity_signature` (Tasks 4-5, line 875-1391), a genuine per-field SET (not `gp_identity`'s first-wins scalars), wired into `hardNo()`'s NPI-conflict check and `score()`'s zip signal. |
| 2 | Four outcomes: new profile / attach to one / new cluster from batch / bridge-merge; plus "strict-conflict cannot bridge" | **COVERED** (first three, real-time) / **DEFERRED WITH CAUSE, with a real gap** (bridge-merge) | New/attach/new-cluster: already real-time via `DeterministicResolver`+`ProbabilisticResolver`. Bridge-merge: plan 8 **deliberately does not move it to resolve time**, keeping it in periodic `Engine::dedup()` (Task 6, incremental-profiling.md:1405-1420). Plan 8's stated reason is that bridging can cascade into an unbounded **transitive** chase ("walking that second identity's own keys for a THIRD identity, and so on"). That reasoning is sound for the *transitive* case, but the page's own worked example (record H hitting P1 via NPI and P3 via license) is the **bounded, first-order** case: one new row's own keys resolve to two *different* existing profiles directly via the index — no transitive walk is required to *detect* that bridge, only to decide how far to chase it afterward. Plan 8's justification does not separate "detect a same-row two-profile hit" (cheap, index-bound, could be resolved immediately) from "chase further transitive consequences of that merge" (the genuinely unbounded part it correctly defers). As written, gp-cami defers even the cheap case to the weekly `gp:reprofile`, leaving a window (up to a week) where two profiles that a single new record's own keys already prove are the same provider stay unmerged. This is a real, if narrow, staleness gap the plan's own reasoning doesn't fully justify — worth a design review, not a blocking defect (it is time-bounded and self-correcting on the next `gp:reprofile`). |
| 3 | Practical notes: incremental adds can only merge; updates/deletes may need a **split**, which incremental can't do cleanly; treat update as delete-then-add; periodic full re-profile required | **PARTIAL, with one clear UNADDRESSED item** | "Adds only merge": consistent with gp-cami's design (no plan adds split machinery to the per-row path). "Treat update as delete-then-add": plan 8 documents that `stg_person` is already fully replaced on every re-sync at the **staging** layer, satisfying delete-then-add there (incremental-profiling.md:1425-1428) — but explicitly states the **identity** level does not follow: `gp_identity.npi`/`dea_number`/etc. are first-wins and never cleared when a source value changes, so "a stale key can keep binding new rows to an identity that, strictly, should have split." Periodic full re-profile: COVERED, `gp:reprofile` weekly. **The split path itself is UNADDRESSED**: `gp_identity.status` has a `'split'` enum value that, per plan 4/individual-vs-entity.md (lines 646, 1101, 2943, 5190, 5309, 5563 — the same fact stated five times across that plan, always as an aside) and confirmed by grepping all of `app/` and every plan, **nothing in the codebase or any of the 10 plans ever writes**. Plan 8 explicitly disclaims fixing this ("This plan does not attempt incremental split logic… This plan does not modify `resolveDeterministic()`/`tierCreate()`/`tierLink()` to also RE-EVALUATE already-linked rows from scratch"), correctly citing the source page's own words that incremental "can only ever merge." That is a fair, well-cited deferral of the *incremental* split — but it means the **general capability to ever split a wrongly-merged identity does not exist anywhere in this programme**, not even in `gp:reprofile` (which does MERGE convergence + signature/block-key refresh, explicitly not re-evaluation of already-linked rows for splitting). No plan owns building split logic. This is UNADDRESSED, not merely deferred, because no future plan is named as its owner and no design-review flag was raised for it (contrast with `gp_board_action`, which 00-PROGRAMME.md §6 explicitly routes to design review). |
| 4 | Determinism (tie-break to higher score); concurrency (partition batches to avoid concurrent bridge races) | **COVERED** | Determinism: `ProbabilisticResolver::match()` keeps the strictly-higher `$bestScore` (line 132). Concurrency: plan 8 Task 6 adds a shared mutex between `gp:sync` and `gp:reprofile` and documents the `mergeIdentity()`/orphaned-link race in detail (incremental-profiling.md:1444-1460), including that no FK exists to catch it — an honestly-flagged residual risk rather than a false "solved." |
