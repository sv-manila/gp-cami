### Ruling on `steward_decision` (audit request #2)

Plan 6 declines to build the table and argues each enum member separately. Taking them one at a time:

- **`confirm` / `reject` — the argument holds, and the substitute is better.** Plan 6 verified a real
  CAMI-side source: `match_actions` (`action_type` ∈ {`confirm`, `resolve`}, `user_id`, `note`,
  `date_created`) mapped by `MatchAction::TYPE_CONFIRMED` / `TYPE_RESOLVED`. Tasks 4 and 6 ingest it
  into `gp_identity_exclusion.link_state` **and** `gp_identity_resolution`. Building a parallel
  `steward_decision` table alongside `gp_identity_resolution` — which already carries
  `action_type`, `decision`, `decision_status`, `resolution_metadata`, `resolved_by`, `resolved_at`,
  a de-dup key `uq_action(system_id, source_action_table, source_action_id)` and an `is_current`
  currency flag — would be a second writer for the same fact. Correct call.

# Where a plan's reason for declining is sound — stated plainly

An audit that flags every deferral as failure is useless. These are right, and several are better
reasoned than the spec they decline:

- **Plan 7's typed exclusion dates** (`excl_date`, `reinstate_date`, `waiver_date`, stored
  `is_active`). Investigated live, ~20 registry prefixes sampled, each shape recorded, one corrupted
  sentinel (`"AREALNULL"`) and one self-contradicting field (`sam2.date_deleted`, identical on every
  row) found and named. The refusal to stub NULL columns nothing will populate, and the refusal to
  infer reinstatement from a row "vanishing" when `matches` has no soft-delete column and no
  evidence rows are ever removed, are both correct. The five-step handover for whoever gets registry
  documentation is the right artifact.
- **Plan 7's `field_authority.exclusion`.** The best-argued deferral in the set: it proves the four
  named values are not source systems in this architecture but values of
  `exclusion_records.exclusion_list_prefix` inside one system, so the config's shape does not
  correspond to anything `Survivorship` can rank. Correctly classified as a design decision.
- **Plan 7's rejection of the doc's `matched_on` enum.** Verified that `streamline_local.matches`
  carries no dob-match or address-match flag, so `name_dob` would assert a corroboration gp-cami
  never performed. The doc is wrong here, not the plan.
- **Plan 6's refusal to build `steward_decision`.** Conclusion right (three of four members already
  covered, and a second writer for `gp_identity_resolution`'s facts would be a defect), reasoning
  partly wrong on `split` — see the ruling above.
- **Plan 6's deletion of `status_severity`.** Traced the entire ingest path (`stg_person_license`,
  `addLic()`, `src_exclusion_record`, `exclusion_records.match` via `Match\Presenter`) to show the
  vocabulary exists nowhere upstream, and left a code comment so the deletion is not read as an
  oversight. Wiring it would have invented a capability on a fabricated source.
- **Plan 6's `gp_board_action` split.** Verified board actions are not a separate source (they
  arrive as `ExclusionList::BOARD_ACTION` typed exclusion lists already flowing into
  `gp_identity_exclusion`) and that the missing columns live in per-registry unstructured JSON where
  `has_active_board_action` has "no safe default". Named a concrete boundary. Programme §6's
  escalation to three explicit options is the right call.
- **Plan 5's deferral of the NPI-replacement trail.** No source feed, external gov-feed ingestion
  already rejected, and the reasoning that a `replaced_by_npi` column with nothing to populate it
  "would look implemented and never be" is exactly right.
- **Plan 5's "fresh" gate.** A same-server mirrored source read on a watermark has no arrival event
  to be late; not faking it was correct.
- **Plan 5b's honesty about its own ceiling.** It declined to fake a fixture case to hide that
  wider blocking delivers less than its scope suggests until the Pass B weights are recalibrated,
  and said so.
- **Plan 2's SSN removal.** "PII duplicated across a trust boundary for no information the caller
  lacked" is the correct argument (the caller supplies the SSN in the request), and Task 8's
  recording of the forfeited property — the hub's clustering is no longer reproducible from a
  from-scratch rebuild, with query 6 to measure *N* before anything is removed, and one
  `gp_resolution_log` row per affected identity as machine-provenance — is the model for how to
  document a cost rather than hide it.
- **Programme §4's single gate ladder and §3's timestamp assignment.** Both prevent real, silent
  defects (five plans re-baselining the same ratchet from five different assumed baselines; four
  plans claiming one migration timestamp, which Laravel resolves alphabetically rather than
  failing). §4's invariant — `precision` 1.0000 and `false_merges` 0 absolute at every rung, never
  lower a floor, never delete an assertion, never remove a fixture record to keep a number up — is
  the right hard line, and the note that it exists because `MatchScorer::score([], [])` returns a
  perfect score is the kind of paranoia this programme needs more of.
